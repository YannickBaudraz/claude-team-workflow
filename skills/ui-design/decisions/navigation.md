# App shell and navigation

Read this before deciding the shell's regions, navigation, header, context switching, landing screen, page tabs and multi-item work.

It answers the Navigation and Starting point axes in `REASONING.md`. Floors: `CRAFT.md`. Favourites, search, narrow screens and the organisation scheme are separate decisions.

## Inputs

- Destinations: count, levels, growth with features or user content.
- Switching frequency; width the content needs; destinations an icon alone identifies.
- Each shell item's scope: product section, system utility, context, page control.
- Contexts: scope of each (app, navigation area, page), count per user, cost of a mix-up.
- Per role: the job on return; arrival by sign-in, switch or deep link.
- Whether a job keeps one item in view while working on another; items per session.
- Existing and sibling shells, and their age.

## Criteria and evidence

- **Regions:** guidance agrees on one scope per region, positions stable across pages and products; convention, untested.
- **Form:** item-count thresholds between forms recur without evidence: convention. Evidence on the menu's side is thin and conflicting. Sources disagree on shell depth, two levels or three; weigh destination count and growth.
- **Visibility:** one practitioner study (179 users on news and shopping sites) found hidden navigation degraded use, more on desktop; no app used daily was tested. Guidance ties an icon rail to daily use and recognisable icons. A lab study of menus, not shells, found fixed order faster than system reordering; most users preferred controlling it.
- **Weight:** sources disagree. A salient shell helps newer users find it; a receding one helps frequent users focus. Vendor accounts report both costs; none is controlled. Name the side and whom it serves.
- **Header:** guidance admits items needed often and from anywhere. Orders differ, unsettled by research: state the principle and keep it.
- **Contexts:** weigh indicator prominence against the cost of a mix-up. Vendor tests found users confusing global with contextual content; one practitioner holds, untested, that the context shown is the one acted on.
- **Landing:** no study compares resuming with a home; guidance matches each option to the job on return.
- **Tabs:** sources agree, untested: a view users would link to or revisit, with its own title, is a location. Check each tab control holds one kind.
- **Several items:** guidance starts from one location, more on request; weigh it against whether a job keeps one item in view while working on another. A study of heavy tab users found reminding the commonest stated reason, and two usage levels. Nothing compares in-app with browser tabs.
- **Fit:** weak evidence backs sibling products sharing structure; weigh departures under "Familiar and new".

## Options space

- **Regions:** which exist, which scope each holds.
- **Form:** top, side, both, rail; shell depth; where deeper levels go.
- **Visibility:** open to hidden, per page type; fixed or customisable.
- **Weight:** salient to receding.
- **Header:** membership, order, priority.
- **Contexts:** selector placement, scaling to many, indicator prominence, what persists after a switch.
- **Landing:** restored state, overview, work queue, home; shared or per role.
- **Page splits:** secondary navigation, navigation tabs, in-page tabs, one page.
- **Several items:** deep links, split view, in-app tabs, windows; who controls it.

## Testing

- Orientation tasks: find a section, resume unfinished work, name the active context after a switch.
- Discoverability of hidden controls with newer users; speed and focus with heavy users.
- For a change: rate disruption by affected usage, users and the old shell's age; announce in proportion; compare with a baseline.

## Recording

In the design model: regions and scopes; inputs behind the form; visibility per page type; weight side and audience; header ranking and principle; context rules; landing per role; each split's location test; multi-item choice and controller; change announcement.
